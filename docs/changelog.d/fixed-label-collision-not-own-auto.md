- **identity: a claimed name that a collision renames never becomes the label the server assigned:** `set_agent_label_resolved` renames a claim of a label another agent holds to `<name>_<uuid8>`, appending this agent's own uuid8. That is also how the mint builds its label (`claude_code-opus_<uuid8>`) and how a knowledge write names an agent with no meaningful label (`Agent_<uuid8>`). So a claim of the bare mint stem (`claude_code-opus`) while another agent held it became this agent's own mint label, byte-identical to the recorded `auto_label`, and `agent_signature` and the knowledge display payload reported `label_source: "auto"` for a name the caller claimed; `docs/ontology/identity.md` listed this as the one exception (#2490). When `<name>_<uuid8>` equals a label the server recorded for this agent, in memory or in `core.identities.metadata` (which the cold-start loader restores), the rename now takes the uuid's first two groups (`<name>_<uuid8>-<4 hex>`), or the whole uuid if another agent holds even that. Every other collision rename keeps the `<name>_<uuid8>` form, and the exception is gone from the ontology. For a knowledge write's `Agent_<uuid8>`, a claim of `Agent` that collides now lands on `Agent_<uuid8>-<4 hex>` instead of the auto-name's own string; it already read `claimed`, because the claim clears the in-memory auto-name, and a claim of the exact string `Agent_<uuid8>` still relies on that clear. Stored labels are not rewritten: an agent whose claim was renamed to its own mint label before this change keeps that label, and it reads `auto` until the agent claims a name again. No tool description, input schema or interface contract changed (#TBD).
