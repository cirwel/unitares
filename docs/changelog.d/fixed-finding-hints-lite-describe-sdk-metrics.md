- **update_finding / store_finding hints, describe_tool lite, SDK get_metrics:** hints on the finding write paths now name something that works as written (observed live, 2026-09-26). The note on a closing update without `closure_class` said `Pass closure_class=['duplicate', 'fix_verified', ...]`, a list value that fails validation for a string parameter, and did not say that `fix_verified` also needs `closure_evidence`. It now names the classes as prose and, for each class, the evidence keys the validator demands, read from the validator's own table. The follow-up call the note names repeats the status just set, `status=<the status just set>`, because a non-owner of a high or critical finding may add notes (and a class) only alongside a cross-agent closing status, and the status-less call was refused to exactly that caller. A closing update that already carried notes is told they are the record rather than that it declares nothing. `CLOSURE_CLASS_PERSISTED` is derived in tests from the three storage update paths, so the note cannot claim the class is stored when it is not, or the reverse. (Where and how the class is stored, and which call the note names, is in this release's entry on `closure_class` being stored; in between the two changes the note pointed at `resolution_notes`, because nothing stored the class then.) The anonymous-writer hint on `store_finding` names how to bind (the `client_session_id` `start_session` returned, else `start_session(force_new=true)`), and the display-name hint passes `client_session_id` to `identity`. `describe_tool(lite=true)` for an alias that pins a router action, or a router narrowed with `action=...`, now leads with what the action's handler requires at call time, marked `(required at call time)`, then the action's own parameters, primary first, and no longer fills from other actions' parameters: `update_finding` lists `discovery_id`, `status`, `resolution_notes`, `superseded_by`, `summary` and `details` where it listed `content`, `details`, `summary`, `discovery_type` and `tags`, and `get_discovery_details` names `discovery_id` where it listed search parameters. A narrowed router view whose `action` has a default says to pass the action (`self_recovery(action='quick')` was described as `reason` alone, which runs `check`). `ACTION_REQUIRED_FIELDS` declares the requirements (`knowledge`; `dialectic` quick's `issue_description`), and `ACTION_FIELDS` gains reads the handlers already made (`knowledge` update, store, get and synthesize; `observe` anomalies, aggregate, audit_events, outcome_evidence and bridge; `dialectic` quick, request, thesis, synthesis and reassign); tests hold both to the handler source for every router that dispatches through an action table. No advertised description or input schema changes. **sdk:** `get_metrics()` returned `MetricsResult.metrics == {}` on every call, because the `check_working_state` envelope has no `metrics` key; both clients now read the reading from `state_summary` and `action_summary` (the canonical payload first when `raw_governance` is present), fill `metrics` with E, I, S, V, coherence, risk_score, verdict and primary_eisv_source, and add `verdict`, `action`, `coherence` and `risk` to `MetricsResult`. The SDK version is not bumped here (#2479).
