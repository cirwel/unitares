- **Stable session ids can no longer be derived from an agent's UUID.** The `client_session_id` that `onboard` and `identity` return was `agent-{uuid[:12]}`, a pure function of the public UUID, so anyone who knew an agent's UUID could compute it and act as that agent. It is now `agent-{uuid[:12]}-{tag}`, where the 20-character tag is an HMAC keyed with a value derived from the server's continuity key (`src/mcp_handlers/identity/stable_session.py`), and rotating that key rotates every id. A keyed id authenticates itself: the resolver accepts it when exactly one identity that is not deleted has that uuid prefix and the tag verifies (an archived agent resolves as archived, so reactivation still works), with no stored binding needed and nothing written, so residents that resume by token or UDS attestation keep working however their bindings expire. A forged tag, an unknown or ambiguous prefix, or a deleted agent is refused with `stable_session_id_rejected`. Because the id is now a credential, surfaces other callers can read store a `csid:` digest of it instead: audit event, tool usage and outcome event rows, knowledge-graph writer provenance (`session_id_at_write`), and every lease's `audit_session`, which the lease plane now stores as the digest at acquire whichever client sent it (a lease-plane release is part of this change). A legacy `agent-{uuid12}` id follows `UNITARES_LEGACY_SESSION_IDS`: `refuse` by default, `log` to accept and log `[LEGACY_SESSION_ID]` during a migration, or `accept`; a server with no continuity key still issues and accepts legacy ids. Clients that store and echo the returned id are unaffected and pick up the new id at their next onboard or rebind; a verified continuity token that embeds a legacy id converts to the keyed one, and runtime observations accept a verifying keyed id without a stored session row. Interface contract 1.31.0.
