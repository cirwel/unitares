- **fleet-identity guard:** tool input schemas are now checked as the prose they are. `scripts/dev/check_fleet_identity_leak.py` flagged a string literal in shipped Python only when the literal *was* a resident name, and #2493 held the served files (skills, `tool_descriptions.json`, the dashboard) to a stricter word-level rule. The schema text fell between the two: a Pydantic `Field`'s `description=` and its `json_schema_extra` `"brief"`, a schema model's docstring (served as the schema's own description) and the alias overrides in `src/alias_schema.py` are Python literals that every connecting agent is served, and a resident name inside a longer description passed. A review of #2489 caught one in `observe`'s `target_agent_id` that the guard had passed. In `src/mcp_handlers/schemas/*.py` and `src/alias_schema.py` those literals now get the served-prose rule: a resident name anywhere, as a whole word in any case, fails the build ("Sentinels" and "vigilant" still pass), and neither `NOT_IDENTITIES` nor `KNOWN_COUPLINGS` defers it. A description built from a module-level constant is read through the constant; other literals in those modules keep the literal rule. The rule is static, because the guard runs where the project's dependencies are not installed, and a test cross-checks it against the schemas Pydantic builds. Current master and the open PR that edits schema text pass with no new exemption. Tool-description text assembled in `src/tool_descriptions.py` is still checked by the literal rule only (#2536).
