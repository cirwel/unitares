- **A failed substrate-claims lookup no longer lets a known resident resume over HTTP (#2682).** A substrate-anchored agent (one with a `core.substrate_claims` row) may resume only over its attested UDS socket, and three gates in identity resolution refuse its UUID over HTTP: the pre-session continuity-token gate, the token rebind (PATH 2.8), and the session and prefix paths (`_substrate_http_reject`). Each caught any exception from the claims lookup and fell through to the ordinary resume, so a database timeout at the wrong moment removed that layer for exactly the agents it protects. The server now keeps the set of claimed UUIDs: every lookup that finds a claim records it (entries are never removed, so a stale read cannot erase a newer one), and a background task reloads the whole table every minute, so an enrollment is known within a minute even if nothing looks it up (a resident enrolled in the minute before an outage, and not yet looked up, is the remaining gap; no enrollment can be committed during one, since enrollment writes to the same database). When the lookup fails on an HTTP request, a UUID in that set is refused with `substrate_check_unavailable`. Until the table has loaded once (a restart during a database outage), the server cannot tell a resident from anyone else, so every such request is refused with the same code and a retry message; after the first load, any other UUID falls through as before, so an unreachable claims table does not block ordinary agents (including the degraded keyed-session resume that relies on Redis while Postgres is down). A caller with a kernel-attested peer PID (UDS) is never refused by this path.
