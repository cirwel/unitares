- **A failed substrate-claims lookup no longer lets an enrolled resident resume over HTTP (#2682).** A substrate-anchored agent (one with a `core.substrate_claims` row) may resume only over its attested UDS socket, and three gates in identity resolution refuse its UUID over HTTP: the pre-session continuity-token gate, the token rebind (PATH 2.8), and the session and prefix paths (`_substrate_http_reject`). Each caught any exception from the claims lookup and fell through to the ordinary resume, so a database timeout at the wrong moment removed that layer for exactly the agents it protects. The server now remembers which UUIDs have a claim: every lookup that finds one records it, a lookup that finds none clears it, and a startup task loads the whole table. When the lookup fails on an HTTP request, a UUID last seen with a claim is refused with `substrate_check_unavailable`; any other UUID still falls through as before, so an unreachable claims table does not block ordinary agents (including the degraded keyed-session resume that relies on Redis while Postgres is down). A caller with a kernel-attested peer PID (UDS) is never refused by this path. The resume still needed its usual proof before; this restores the extra substrate layer during an outage rather than adding a new requirement.
