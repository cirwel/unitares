- **agent response envelopes:** the write aliases `store_finding`, `update_finding` and `record_result` no longer repeat their canonical payload under `raw_governance` by default, extending the omission the read aliases and routine `sync_state` already had. Each acknowledgement keeps what a caller needs next: `success`, `next_action`, `agent_uuid` (taken from the response's `agent_signature`) with a compact `written_as` giving the writer's `agent_id`, `display_name` and assurance tier, `caller_proven` and `proof_origin` (on `record_result` only when its binding was not server-inferred, because `outcome_event` signs nothing for a server-inferred one); `discovery_id`, write-time warnings (failed supersession, truncation, anonymous writer, unclassified closure) and `consolidation_hint` for the finding writes, plus on `store_finding` a bounded `related_discoveries` store-time similarity snapshot (at most five rows, each an id and a summary preview of at most 120 characters), since a later details read returns the stored record but not the warnings or those previews (the snapshot's ids are the stored record's `related_to`, so a `store_finding` ack that carries the snapshot does not repeat them as `state_summary.related_to`; `update_finding`, and a `store_finding` with no snapshot, keep the record's `related_to` ids); and `outcome_id`, `is_bad`, `idempotent_replay`, `unverified_fields` and any handler `identity_warnings` for `record_result`. `raw_governance_hint` names what is still reachable and never suggests repeating the write: `response_mode="full"` on a later `record_result` (its older `include_semantics` spelling still works, including over `/mcp/`; there is no read by outcome id, so an ack's own outcome payload cannot be fetched again), and a `knowledge(action="details", discovery_id=...)` read for the finding writes, which returns the stored record rather than the ack's payload (the canonical `knowledge` tool also returns their payload directly; `response_mode` is not a full request on these two aliases, because canonical validation defaults `knowledge`'s `response_mode` to `"full"` and the envelope cannot tell a caller's request from that default, and their `/mcp/` schemas do not declare it). Since neither route fetches the omitted payload, these acks do not set `raw_governance_available`, as a routine `start_session` does not. A write whose record id the envelope cannot lift keeps the canonical payload. `start_session` and `request_review` are unchanged. Identity refusals and error payloads still pass through whole. Measured on recorded acknowledgements re-rendered locally from their canonical payloads (2026-09-25, p50, n=5/4/5): `store_finding` 5,412 B to 1,222 B, `update_finding` 5,678 B to 1,663 B, `record_result` 5,505 B to 1,579 B. None of the recorded `store_finding` payloads carried a `related_discoveries` snapshot; one adds at most about 1 KB to the ack (five rows at the preview bound). No input schema changes, so the interface contract version and digests are unchanged.
