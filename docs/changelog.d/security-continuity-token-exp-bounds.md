- **A continuity token's `exp` must be one the server could have written.** Token resolution read `exp` with `int()`, so a finite but absurd value (`1e308`, a 400-digit integer) read as a token that never expires, and a non-integer one (`1.5`, `true`) was truncated into a readable expiry. Resolution now refuses a token whose `exp` is not a JSON integer or lies more than the one-hour continuity TTL plus the 30 s clock-skew tolerance ahead of now, and the PATH 0 freshness observation reports the same token as expired with `token_exp: null`, as its docstring promised. `create_continuity_token` caps `ttl_seconds` at that TTL, so no token the server mints falls outside the bound. Tokens are HMAC-signed with the server's key, so reaching this needed a token signed with that key; it is hardening, not a closed hole. Tokens the server minted resolve as before, and PATH 0 still accepts an expired or unreadable-`exp` token as ownership proof, because it never reads `exp`.
