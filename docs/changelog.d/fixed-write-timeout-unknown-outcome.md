- **write timeouts:** a tool call that can write no longer answers its timeout with advice to try again. The `@mcp_tool` timeout ends the wait for the reply, not the work. On 2026-09-27 an `update_finding` on the AGE backend returned `TIMEOUT` with "Try again with simpler parameters" after its row had committed, and because `resolution_notes` append, following that advice writes them twice. The timeout reply for a write, admin or unclassified call now says the outcome is unknown and the change may have been saved. It carries `outcome: "unknown"`, `operation` and `call_started_at`, and its recovery names the read that settles the question before any retry: `knowledge(action='details', discovery_id=...)` and its `updated_at` for a knowledge update, the caller's newest findings for a store or note, and `describe_tool` for other writes. The class comes from the `operation` metadata that `describe_tool` already reports, resolved per router action. `error_code` stays `TIMEOUT`, `error_category` stays `system_error`, and read tools keep the reply they had. Separately, the AGE update no longer waits for the embedding refresh it runs after committing. The first embedding in a process imports sentence-transformers and loads the model, and that load is what outlasted the 10 s timeout in the incident; the refresh now runs as a tracked background task (#2543).
