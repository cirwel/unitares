- **write timeouts:** a tool call that can write no longer answers its timeout with advice to try again. The `@mcp_tool` timeout ends the wait for the reply, not the work. On 2026-09-27 an `update_finding` on the AGE backend returned `TIMEOUT` with "Try again with simpler parameters" after its row had committed, and because `resolution_notes` append, following that advice writes them twice. The timeout reply for a write, admin or unclassified call now says the outcome is unknown and the change may have been saved. It carries `outcome: "unknown"`, `operation`, `call_started_at` and `settled_by`: the reply time plus the pool's 30 s command timeout, after which a database statement still running at the timeout has finished. `settled_by` bounds nothing else. The recovery offers a resend only where the work is bounded by `settled_by` and the read it names covers everything the call would have written, and then only on a read after `settled_by`. That holds for a knowledge store, note or update, each of which commits one database transaction per row. Every other write, for example `export(action='file')`, whose file write runs on an executor thread that outlives the cancelled await, gets no resend step: its reply says the outcome cannot be settled by reading, because a tool can also write files, start background tasks or call other services that finish later, and tells the caller to inspect the effect with a read-only tool (`describe_tool` lists them) and not to send the call again blind. For a knowledge update, every field it sends is set, not added to, except `resolution_notes`, so the check is `knowledge(action='details', discovery_id=..., length=98304)`, which reads all of details up to the largest value an update stores, paging on while `has_more` says a row is longer. The caller looks anywhere in details, not only at its end, since another writer can append after it, for the block this call would have written: a `Resolution notes (<time>):` line stamped at or after `call_started_at`, followed by its text. The text alone proves nothing, because an earlier block can hold the same words. The update writes all its fields in one statement, so a found block, when every other field sent also shows the value sent, shows the whole update landed and nothing of it is sent again (a block alone can be another call's that sent the same notes, so the caller does not resend blind), except that an update with `superseded_by` records its edge in a separate write afterwards, so the reply adds a step to run the idempotent `knowledge(action='supersede')` once the fields are confirmed; the caller resends only if the block is absent from the whole of details. An update without `resolution_notes` only sets fields, so it can be sent again after `settled_by`. `updated_at` settles nothing, because any writer's update moves it. For a store or note the check is a queryless `knowledge(action='search')` filtered to the author the handler records (the bound identity, the anonymous `anonkg_*` pseudonym, or the `agent_id` the call passed) and to rows created between `call_started_at` and `settled_by`, newest first, archived and cold rows included, limit 100. It needs no bound identity, and `check_arguments` carries it as arguments. A relevance search could lose the row off its ranked page and match another writer's row with the same summary. The window lookup reads `knowledge.discoveries` on both backends, so a list below the limit is every row that author created in the window, each with its full details; a single store is matched on summary and details together, both for finding its row and for deciding it may be resent, since the same writer can store two rows with one summary in the window; a note up to the summary limit is matched exactly, since it is stored as sent, and a longer one is matched when its text is the row's summary, nothing or only whitespace, then its details, since it is split between the two and the split drops the whitespace it falls on; one over the combined limit is first cut to it and marked `... [truncated]`. The reply says when the author id is not the caller's alone, and then only an absent row is proof. A store with `supersedes` marks the old row superseded in a second write the list does not show, so its reply adds a step to run `knowledge(action='supersede')` once the new row is found, whatever the old row shows: it sets a status and merges an edge, so it adds nothing twice and repairs an edge a timeout between the two writes left missing. A batch store (`discoveries`) commits each item on its own, so a timed-out batch can be partly saved. Its reply says how many items the batch held and never has the caller resend the whole batch. Its lookup includes each row's full details, and the caller compares each item with the rows by its summary and details together, not by summary alone, and resends only the items no row matches. Those two fields are stored as sent (cut short when long); `discovery_type`, severity and tags are normalized when stored, so the caller does not match on them. Items that agree on summary and details cannot be told apart, so once a row matches them the reply says resending cannot be made safe for them. `onboard` (and `start_session`) and `identity` are listed as reads but can create an identity, so their timeouts get this reply too, with a recovery that says a repeat creates another identity. A call that names its binding with `client_session_id` is told to read that binding instead, unless it asked for a new identity: `force_new=true`, or `resume=false` on `onboard`, read as the handler reads it, which mints a new identity beside the named binding. On `identity`, `resume=false` is the schema default and the call reads the binding. The class comes from the `operation` metadata that `describe_tool` already reports, resolved per router action. `error_code` stays `TIMEOUT`, `error_category` stays `system_error`, and read tools keep the reply they had. On the AGE backend a windowed query whose SQL read fails now raises instead of returning no rows, as the postgres backend already did, so a failed read is not taken for an empty window; semantic search's in-memory fallback, which only ranks candidates, still degrades to none, so a hybrid search keeps its full-text results. Separately, the AGE update no longer waits for the embedding refresh it runs after committing. The first embedding in a process imports sentence-transformers and loads the model, and that load is what outlasted the 10 s timeout in the incident; the refresh now runs as a tracked background task, one pass at a time per discovery so an older pass cannot store stale text last (#2543).
