- **Server-verified finding provenance (`findings` agent token scope):** `UNITARES_HTTP_AGENT_TOKENS` now supports the `findings` scope for `POST /api/findings` (isolated from `checkin`/`outcome`/`knowledge_store` on `POST /v1/tools/call`). `POST /api/findings` strips any caller-supplied `provenance_verified`, `verified_actor_agent_uuid`, `provenance_source`, and `provenance_mac` fields and stamps them server-side (`provenance_verified: true` + canonical `verified_actor_agent_uuid` only for a valid per-agent `findings`-scoped token; `false` / `null` for trusted-network, dashboard-session, and shared static bearer callers), partitions finding dedup by provenance trust tier and verified actor UUID so unverified or other-actor posts cannot suppress verified findings, and preserves both top-level fields through event storage, `/api/events`, and WebSocket broadcast. Audit-DB backfill authenticates persisted provenance via an internal HMAC-SHA256 `provenance_mac` (never returned by `/api/events`, `/api/incidents`, or `/v1/lifecycle/recent`) keyed by `UNITARES_AUDIT_PROVENANCE_SECRET` when configured (persisting across restarts and unaffected by `UNITARES_HTTP_AGENT_TOKENS` rotation) or an ephemeral per-process key when unset (failing closed across restarts). `agents/common/findings.py` and Vigil accept optional `UNITARES_FINDINGS_AGENT_TOKEN` with safe fallback to `UNITARES_HTTP_API_TOKEN` / `UNITARES_MCP_BEARER_TOKEN` when unset.
