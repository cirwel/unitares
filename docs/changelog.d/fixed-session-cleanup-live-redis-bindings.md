- **session cleanup:** the six-hourly `session_cleanup_task` no longer deletes a Redis session binding that is still in use. A `core.sessions` row expires 24 hours after bind unless a lookup reaches PostgreSQL, but a lookup served from Redis slides only the Redis key's TTL. The cleanup deleted `session:<key>` for every expired row, so a long-lived client that kept resolving through Redis lost its binding at the next pass. Every later call then missed both stores and was refused as `pg_session_missing` until the client re-onboarded. From 2026-09-01 to 09-07 this stranded three discord-bridge keys. Each flood of misses began right after a pass that deleted one Redis key and lasted until the bridge restarted: 74,750, 22,298 and 128,200 miss rows. The cleanup now reads each key's TTL first. It deletes only a key with no expiry (TTL -1), which is the orphan the delete was added for. It leaves a key with a positive TTL for Redis to expire once its client goes idle, and a key whose TTL cannot be read. Its Redis awaits are now bounded. The PG rows are deleted as before, and the log line adds the number of live bindings kept. This does not cover the 09-16 to 09-24 flood (994,848 rows). That one began when Redis restarted from a snapshot older than the bridge's binding, and durability of Redis-only sessions is a separate question (#TBD).
