- **observe:** `observe(action="agent")` resolves every identifier `agent(action="list")` prints for a non-operator caller, and no longer returns the registry UUID to that caller. The listing shows `{public_agent_id}_{uuid8}` in place of the UUID, but the resolver compared the target with the unsuffixed stored id, so the printed handle answered "not found in active metadata" for an agent that had checked in the same day. The resolver now compares against exactly what the listing prints (`lifecycle.disclosure.listed_agent_identifier`), including the `agent-redacted-<digest>` fallback. Separately, a target that resolved came back with its full UUID in `agent_id`, which undid the listing's redaction with one more read. The returned id now goes through the listing's disclosure rule (`lifecycle.disclosure.visible_agent_identifier_for_caller`) with no exception: the operator and the observed agent get the UUID, anyone else gets the listed identifier with `uuid_redacted: true`, including a caller who passed the UUID. A listed identifier that two agents share, or that another agent has taken as its label, is refused with `AMBIGUOUS_TARGET` instead of routed to one of them. Two identities under one plain label still resolve to the first match, as before. A non-operator client that read a UUID out of an observe response now receives a handle. Not covered: `observe` `similar` and `anomalies` still return peer UUIDs, knowledge-graph search results carry writer UUIDs, and the `target_agent_id` description is unchanged; the listing's redaction is therefore not yet a boundary, and reconciling it is an identity-contract decision (#2736).
