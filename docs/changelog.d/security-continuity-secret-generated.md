- **The continuity token secret is the server's own.** Continuity tokens prove ownership of an agent, and under strict identity they are what lets a caller resume one by UUID. Their signing key used to fall back to `UNITARES_HTTP_API_TOKEN` (then `UNITARES_API_TOKEN`), so anyone holding that bearer could sign an ownership proof for any agent, and `docker-compose.yml` set it to a published default. Now, when `UNITARES_CONTINUITY_TOKEN_SECRET` is unset, blank or that published value, the server generates a key at startup in `data/secrets/continuity_token_secret` (mode 0600; `UNITARES_CONTINUITY_TOKEN_SECRET_FILE` moves it) and signs with that. A key file that is a symlink, owned by another user or readable by group or others is refused, and continuity tokens stay off until it is fixed. The API tokens are never used. Effect grants share the key and change with it. Upgrading an install that relied on either fallback invalidates its outstanding continuity tokens and effect grants once: clients onboard again (`start_session(force_new=true)`). A resident anchor holding such a token stops resuming: move the anchor file aside, then re-provision it with `scripts/ops/provision_resident_anchor.py --apply` from the server's checkout (the provisioner leaves an anchor that already names the same UUID untouched, so it does not refresh the token in place). Deleting the generated file and restarting rotates the key. A deployment that already sets `UNITARES_CONTINUITY_TOKEN_SECRET` to its own value sees no change, and its tokens keep verifying across the upgrade.
