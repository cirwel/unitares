- **knowledge updates bound the details value they store; the lifecycle's dead PG-sync block is gone:** `resolution_notes` are appended to a finding's `details` as a timestamped block, and nothing bounded the result, so repeated closing notes (or one long log excerpt) grew the field without limit. On the AGE backend `details` is a Cypher-interpolated node property and `GraphMixin._sanitize_cypher_param` refuses any string over 128 KiB; the whole update, status included, rolled back and the caller was told `Discovery '<id>' not found` for a finding that exists. The update handler now measures the value it would store (the stored details, or the details the call sends, earlier notes included, plus the new block) against `MAX_UPDATED_DETAILS_LEN` (96 KiB, in `src/mcp_handlers/knowledge/limits.py`) and refuses an update over it with `INVALID_PARAM` before anything is written. The recovery gives the number of characters of notes that would fit, or, when the stored details leave no room, says to close without notes and record them as a new finding that responds to this one. A `details` replacement sent without notes is held to the same bound, since it is the same stored field. A finding stored at the 64 KiB details cap still takes about 32 KiB of notes; status-only updates are not measured. `KnowledgeGraphLifecycle._batch_update_status` no longer carries its second "PG sync" write: it imported `get_postgres_backend` from `src.db.postgres_backend`, which never existed, and swallowed the `ImportError` at debug level, so it never ran. Both backends' `update_discovery` already write `knowledge.discoveries` (the AGE backend in the same transaction as the graph node), so lifecycle behaviour is unchanged (#2530).
