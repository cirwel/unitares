- **agent locks (fcntl backend):** two writers could hold the same agent's lock at once. The stale-lock check released its probe lock and then unlinked the file, and acquirers never checked which inode they had locked, so an acquirer could lock the orphaned file while a newcomer locked a fresh one at the same path. It also removed files that were still held when the recorded pid looked dead or the timestamp looked old. A lock file is now stale only when no process holds it: removal (`state_locking.remove_lock_file_if_free`) probes with a non-blocking exclusive flock and unlinks while still holding it, and every fcntl acquirer (sync, async, and the `DistributedLock` file fallback) re-checks after `flock()` that it holds the file currently at the path, reopening if not. A test with four writer processes and a concurrent cleaner fails on the old code and passes now. The `admin(cleanup_locks)` / `cleanup_stale_locks` tool, which derived its root as `src/` and so swept a directory nothing writes to while reporting success, now sweeps the lock writer's directory and reports the active lock backend. The update-timeout path no longer sweeps (a timeout means a live holder) and no longer advises running the cleanup tool. The default advisory backend creates no lock files and is unaffected.
