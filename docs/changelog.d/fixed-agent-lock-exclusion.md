- **agent locks (fcntl backend):** two writers could hold the same agent's lock at once. The stale-lock check released its probe lock and then unlinked the file, and acquirers never checked which inode they had locked, so an acquirer could lock the orphaned file while a newcomer locked a fresh one at the same path. It also removed files that were still held when the recorded pid looked dead or the timestamp looked old. A lock file is now stale only when no process holds it: removal (`state_locking.remove_lock_file_if_free`) probes with a non-blocking exclusive flock and unlinks while still holding it, and every fcntl acquirer (sync, async, and the `DistributedLock` file fallback) re-checks after `flock()` that it holds the file currently at the path, reopening if not. A test with four writer processes and a concurrent cleaner fails on the old code and passes now; it guards the acquirer re-check, and a deterministic test pins that the cleaner unlinks while its probe still holds the lock. `DistributedLock.force_release` keeps a held file lock instead of deleting it (deleting a held flock's file never released the holder; it only let a second one in), and its acquisition timeouts raise `LockTimeoutError` too. The `admin(cleanup_locks)` / `cleanup_stale_locks` tool, which derived its root as `src/` and so swept a directory nothing writes to while reporting success, now sweeps the lock writer's directory and reports the active lock backend. Lock-acquisition timeouts now raise `state_locking.LockTimeoutError` (a `TimeoutError` subclass), and the update path catches only that: it no longer sweeps (a lock timeout means a live holder) or advises the cleanup tool, and a `TimeoutError` from the work done under the lock is no longer reported as `LOCK_TIMEOUT`: `process_agent_update`'s fail-open branch reports it as an unexpected error. On the fcntl paths only the `flock()` call is treated as contention now, so an `OSError` raised by the caller's own code inside the lock (a `TimeoutError`, a `ConnectionError`) reaches the caller once with the lock released, instead of surfacing as a `TypeError`. The default advisory backend creates no lock files and is unaffected.
