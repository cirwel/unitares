- **the knowledge-graph lifecycle counts only the moves the backend made:** `KnowledgeGraphLifecycle._batch_update_status` awaited each `update_discovery` and dropped its result. Both backends return False for an update they did not make (the Postgres backend when no row has the id, the AGE backend when its query fails and rolls back), so a refused archive or cold move was still counted in the cleanup summary, logged as done, and returned as moved. Before migration 071 this is what happened to every classified resolved row: the AGE update refused the archive on each run, and each run reported the row archived. Each pass now returns only the ids the backend confirmed, and `ephemeral_archived`, `discoveries_archived`, `discoveries_to_cold` and `tags_canonicalized` count only those; the tag-canonicalization pass had the same dropped result and is fixed the same way. A refused or raising update is one row's failure: the rest of the pass still runs, the row keeps its status and is a candidate again next run, one warning per pass names up to 20 of the ids with the exact count, and the summary's new `failed_updates` map gives, per affected count, the number that failed and the same bounded sample of ids. It is empty when nothing failed and always empty in a dry run. The in-process lifecycle health record reads `degraded` with the per-pass numbers after a run with failed updates, where it read `healthy`. Existing summary keys and their types are unchanged, so the cleanup tool response, the SDK's `CleanupResult.cleaned_total` and the startup and periodic sweeps read the same fields, now with the real counts (#2567).
