- **`identity(force_new=true)` now mints without consulting the session's existing identity (#2692).** The `identity` tool skips its session-key resume when `force_new` is set, then calls `handle_identity_v2`, which resolved the same session key again without passing `force_new`. The resolver therefore ran the checks and lookups that belong to a resume. The confirmed consequence came with keyed session ids (#2702): the resolver validates a presented stable session id on every call that is not `force_new`, so `identity(force_new=true)` sent with a forged keyed id (or, once `UNITARES_LEGACY_SESSION_IDS=refuse`, a legacy `agent-{uuid12}` id) got back a refusal, which the handler then read as a resolved identity and failed with a key error instead of minting. `force_new` now rides through to the resolver, which skips every lookup path and mints, exactly as `start_session(force_new=true)` does through onboard. Calls without `force_new` are unchanged: they still go through the session-key resume first, and the resolver call after it keeps its previous arguments.
