- **identity guidance for a dropped `client_session_id`:** a caller that omits its id now gets pointed back to that id instead of to a second mint or to `continuity_token` on every call. (1) The unbound `check_working_state` / `get_governance_metrics` payload and the glossary `unbound` entry lead with "if this process already called start_session, repeat this read with the client_session_id it returned", then `start_session(force_new=true)` for a process with no identity. The glossary meaning is now "No caller-proven identity on this call"; the `⚪ unbound` status and `unbound` verdict are unchanged, and the payload still names no uuid. (2) The strict (`STRICT_IDENTITY_REQUIRED`) `sync_state` / `process_agent_update` refusal for a server-inferred binding leads with retrying with the id `start_session` returned. `continuity_token` appears only inside `identity(agent_uuid=..., continuity_token=..., resume=true)`, followed by a retry with the id that call returns. The read-only option is `check_working_state(client_session_id=...)`, and `do_not` warns against minting a second identity to clear the refusal. A mint (`start_session(force_new=true)`) is offered last, only to a process that never called `start_session`, since the pin can resolve such a process to a co-located sibling. The hint quotes the same remedy text as the `identity_assurance.how_to_strengthen` it embeds; that breadcrumb, on both the write and identity paths, now says to pass the id the rebind returns. (3) A pre-onboard read on `/mcp/` now counts an `X-Session-ID` header as proof when `derive_session_key` keyed the call on it (step 4, `caller_asserted`). A header-only read therefore resolves on the same key a header-only write on the same connection already used, as REST reads already did. A header naming no session still reads `unbound`. `Mcp-Session-Id`, `X-Client-Id` and the OAuth client id are not counted. The typed wrapper's transport injection, which looked like the cause, never runs on a direct `/mcp/` call because FastMCP None-fills the argument first; it is now documented as unreachable and pinned by a test that goes through FastMCP validation. (4) The shared contract rule 2 and `docs/ontology/identity.md` say that when the minting call carries no session or client signal of its own (bearer-token `/mcp/` or plain REST), its weak / `caller_proven: false` assurance describes that call, not later threading, and that threading is confirmed on the next call with `check_working_state(client_session_id=...)` or `identity(client_session_id=...)`; rule 2 adds that a pin-resolved `sync_state` is refused under strict identity. `identity.md` also says that refusal is not a general write gate: a low- or medium-severity `store_finding` can still be attributed through the pin. `governance-lifecycle` says bearer-token `/mcp/` keeps no binding between calls (an OAuth client's binding is per client), gives an `X-Session-ID` header as an example of a transport session signal, and no longer tells a live process to mint again when a call resolved only by weak signals.
