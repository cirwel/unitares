- **identity: a target named through `use_tool` resolves its session as it does named directly; both read gates judge session headers by one predicate; refusals and `label_source` stop pointing at a second identity:** (1) The nested `/mcp/` `use_tool` path no longer copies the transport session (an `X-Session-ID` header, `Mcp-Session-Id`, the OAuth or `X-Client-Id` client, or the IP:UA fingerprint) into a session-injected target's `client_session_id`, flagged transport-injected. A direct call never did, since FastMCP None-fills the argument first. So a header-only `sync_state` through `use_tool` now derives `x_session_id` / caller-asserted and passes `STRICT_IDENTITY_REQUIRED` as it does directly, a proof-less `check_working_state` through `use_tool` reads `unbound` instead of resolving a server-inferred binding and serving its state, and a fingerprint-only write reaches the step-7 onboard pin. An explicit outer `client_session_id` still reaches the target as caller input. The parity is for the session only: `use_tool` does not apply the target's `/mcp/` argument schema, so an argument that schema drops (`agent_id` or `agent_uuid` on the metrics tools) still reaches a nested target. (2) The REST pre-onboard read gate no longer counts an `X-Client-Id` / `X-MCP-Client-Id` header as proof: it names a client, not a process, so two processes of one client could read each other's state. Both read gates now judge a session header through one predicate (`transport_session_is_read_proof`), applied to the source that produced the session key, under which only `X-Session-ID` proves a read; on REST that holds whether the header reached the derivation as an id the transport put in the body or because the body's `client_session_id` was null, empty or invalid. The predicate covers session headers only: a `client_session_id` the caller sent and a verified `continuity_token` still prove a read on both transports, and `/mcp/` also still counts an `agent_uuid` argument and a UUID `X-Agent-Id` header, which the session-key derivation ignores, so such a read resolves on the transport's own signals (the onboard pin, for example) as server-inferred. REST writes are unchanged. No caller in this repo, the governance plugin, the discord bridge, anima-mcp or the host adapter sends `X-Client-Id`. (3) The strict refusal for a required call that resolved no identity picks its recovery from the resolver's result on both transports (`identity_bootstrap.unbound_call_refusal`). A session miss no longer leads with `onboard(force_new=true)`: with no `client_session_id` of the caller's own on the call, it leads with retrying with the id `start_session` returned, then the `identity(agent_uuid, continuity_token, resume=true)` rebind, and offers a mint only to a process that never called `start_session`; with a caller-sent id that names nothing, the rebind leads and the mint is for a process that cannot rebind. On REST, where every unbound required call got the default mint-first refusal, a resume the hijack guard rejected, a substrate-anchored resident over HTTP and a token naming an inactive agent now get the cause-specific hint `/mcp/` gives. A session lookup that raised (`pg_lookup_exception`) gets the server-failure retry on both transports instead of a mint-first recovery. The recovery sentences the strict write refusal and the unbound read quote now live in `identity_bootstrap` with their text unchanged. The bare-onboard lineage refusal keeps its mint-first defaults. (4) `agent_signature` and the knowledge display payload report a label the server assigned as `label_source: "auto"` instead of `"claimed"`: the mint's `claude_code-opus_<uuid8>` label (logged as `[AUTO_NAME]`), which the mint now records as `auto_label` in the identity metadata, and the `Agent_<uuid8>` name a knowledge write gives an agent with no meaningful label (recorded in memory, where that name is set). A label is server-assigned while it still equals the record, so a claimed name renamed `<name>_<uuid8>` by a collision still reads `claimed`. Agents minted earlier, and lazily persisted mints, carry no record and read as before. No tool description or input schema changed. Every surface that branches on whether the caller sent its own client_session_id (the REST prebind and strict gate, the /mcp/ session-miss refusal, both unbound metrics reads) now uses one rule: an id the transport put there, or that a REST session header supplied, is not the caller's, and one that normalizes to nothing was never looked up; so a header-only REST read gets the same no-id recovery as on /mcp/. The unbound read's caller-sent branch leads with the identity(agent_uuid=..., continuity_token=..., resume=true) rebind, as the strict refusal does, with the mint under otherwise (#2478).
