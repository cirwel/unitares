## 1. Problem

Agents report their own work through check-ins. The evidence about that work mostly lives on GitHub: CI results on the PR, review records from the review gate, and whether the change merged. None of it reaches UNITARES today unless an agent records it by hand.

The 2026-10-23 session that built #3045–#3050 shows the gap. UNITARES recorded 45 check-ins for that agent up to 12:53 UTC. 44 were hook readings of turn shape (`substrate_interpretation`) and one was the agent's own report. All of them read `approve`, risk 0.00–0.29. The PR record for the same hours holds 22 review findings fixed before merge, one CI failure (a 1400-byte budget breach), and one corrected claim about a local test run. A reader of UNITARES alone would see a quiet session. A reader of GitHub would see the real one.

Neither hook readings nor self-report carry that evidence. Self-report is the right source for claims and intent. It is the wrong source for evidence about mistakes: an agent cannot report a mistake it does not know it made. Evidence should arrive on its own, and a mistake should show up as a contradiction between a claim and a result, not depend on a confession.

## 2. Principle: a mistake is a path, not a mark

Recorded as an operator direction on 2026-10-23. The observer and every view of its events follow it.

| Stage | Meaning |
|---|---|
| introduced | someone did real work; carries no weight on its own |
| caught by the agent | self-checking worked |
| caught by review or CI | the gates worked; time to catch is the useful number |
| fixed | the path closed; time to correction is the useful number |
| escaped | merged, deployed or user-visible with the defect: a negative signal |
| repeated | the same class of mistake again: a learning signal |
| concealed or misreported | a claim contradicted by evidence and not corrected: the case accountability exists for |

Failure counts are not a measure. A red CI run on an open PR, a review finding, and a `test_failed` row written during test-first development are all the process working. Nothing in this design pauses, ranks or penalises an agent.

## 3. What exists

- **Attribution key.** Every agent-authored PR body ends with `UNITARES agent: <uuid>` (global contract, operator decisions 2026-10-20 and 2026-10-23). The uuid resolves in UNITARES to the agent's identity.
- **Structured review records.** `scripts/dev/review_gate.py` posts PR comments that open with `<!-- unitares-review v1 key=… verdict=CLEAN|FINDINGS|FAILED findings=N disposed=0|1 reviewer=… head=… -->` (marker `unitares-review v1`, `review_gate.py` `MARKER`). `FAILED` means the review was unavailable or incomplete. `disposed` is a flag, not a count. The reviewed commit is the separate `head=` attribute, which legacy records lack. A disposition is a new record with the same key and head as the review it answers. The gate admits a marker comment only from an owner, member or collaborator, or from the registered App (`trusted_review_comment`); a pasted marker from anyone else is ignored.
- **CI.** GitHub check runs and workflow runs per PR head, each with a run id and attempt number, readable with any GitHub token that can read the repository.
- **Ingestion routes.**
  - `POST /v1/harness/outcome` writes `audit.outcome_events` under an operator-asserted `agent_uuid`. It feeds outcome analysis, so stage 1 does not use it (§5).
  - `POST /api/findings` takes findings from "any producer (a resident, a doctor check, a host hook)": `type` must end in `_finding`, `severity` is one of `info|low|medium|warning|high|critical`, and `fingerprint` dedups within a 30-minute in-memory window that a server restart clears (with an optional `change_token` for emit-on-change). It persists to `audit.events` through `broadcast_event` and appears on `/ws/eisv`.
- **Readers.** `GET /v1/timeline` (#3045) serves six kinds. Lifecycle, knowledge and lineage come from `audit.events` by type, which is the path a new kind would extend; check-ins come from `core.agent_state`, outcomes from outcome events and dialectic from session rows. Check-in excerpts on `/v1/timeline` are `portal-live-timeline-v0.md` §4 item 1, a separate PR. The Timeline tab (#3047) is in review. The live pane in `portal-live-timeline-v0.md` consumes `/ws/eisv`, and its adapter maps only the frame types it lists.

## 4. Design

A small observer polls GitHub for open and recently merged PRs whose body carries the `UNITARES agent:` footer, and emits one event per new fact. Every type is `github.*`:

| Event | Fields | Fingerprint |
|---|---|---|
| `github.pr_opened` / `github.pr_merged` / `github.pr_closed` / `github.pr_reopened` | pr, repo, head_sha, agent_uuid | the open is `repo#pr:opened` (opening is not a GitHub timeline event); each later change is `repo#pr:state:<GitHub timeline event id>`, so a close, reopen and second close are each their own fact. The `closed` event that accompanies a merge is folded into `pr_merged`. The stage 1 GitHub JSON fixtures confirm both API facts |
| `github.ci_result` | pr, head_sha, workflow or app, run or check id, attempt where the source has one, conclusion, failed_jobs | Actions: `repo#pr:ci:run_id:attempt`; other check apps: `repo#pr:check:check_run_id:conclusion`, because an app may rewrite a completed check run with a new conclusion. Emitted at completion, so a re-run on the same head is its own fact. The repository's own `review` check is skipped: `review_record` already carries what it reports |
| `github.review_record` | pr, head_sha (from `head=`, else null), key, verdict, findings, disposed, reviewer | `repo#pr:review:<comment id>`: every record comment is its own fact, so a disposition, a second model family on the same head, a FAILED record and its retry, and a re-run on an unchanged diff all stay. Only comments that pass the gate's `trusted_review_comment` rule are read. The fields are the marker's raw values; the gate's own reading adjusts some (a FAILED record with partial findings counts as FINDINGS, a disposition without complete entries as undisposed), so the event says `raw: true` and the reader applies the gate's rules or links to the gate's check |
| `github.claim_checked` | pr, head_sha, checkin_state_id, excerpt, ci_conclusion, status (`open` or `closed`), closed_by | derived (stage 2): an agent-authored check-in by the PR's agent, its excerpt claiming success, paired with the next CI result on that PR. A pair that agrees is not emitted. A pair that disagrees opens, and closes when a later agent check-in or PR-body edit corrects the claim or a later run on the PR passes. Only a pair still open when the PR merges is the "not corrected" case of §2. Fingerprint `repo#pr:claim:<checkin_state_id>:<status>`, so the opening and the closing are two facts. The window and the claim pattern are telemetry settings, not verdicts |

Every event carries `agent_uuid` (the subject) separately from the observer's own id (the producer). Dedup must be durable: the observer keeps the set of fingerprints it has emitted in its own state store, and under option B the route also refuses a repeated fingerprint. The server's 30-minute in-memory window is not relied on. Without durable dedup, a 5-minute poll would write each fact again every 30 minutes and after every restart, each time as a permanent `audit.events` row.

**Where it runs.** An optional member under `agents/github_observer/`, public surfaces only (`federation-component-boundaries-v0.md`): it reads GitHub with a token the deployment supplies and writes through one UNITARES route. It never reads core tables by SQL. It is generic: any install whose agents sign PRs can run it with its own token, and it never branches on agent or resident names. The maintainer's deployment supplies its App runner's token. A deployment schedules it, a launchd job for the maintainer. It is never part of the server process.

**Write path: the open decision in §8.**
- **A.** Post through `POST /api/findings` as `github_ci_finding`, `github_review_finding` and so on. This needs no server change. It costs semantics: everything on that route reads as a finding (something wrong). That runs against §2, and a passing CI run is not a finding. Findings also reach the Discord bridge, and the live pane discards `*_finding` frames, so A gives no live view without a further pane change.
- **B.** A narrow route, `POST /v1/external/events`, gated by the operator credential and accepting only `github.*` types with a subject `agent_uuid`. It writes `audit.events`, refuses a repeated fingerprint, and broadcasts. It is one new route and one allow-list, with neutral semantics. The credential gate makes it an operator-reserved auth decision.

The recommendation is **B**. A is a usable interim if the operator prefers no server change.

**Reading.** `/v1/timeline` gains a seventh kind, `external`, read from `audit.events` like lifecycle and knowledge. Once the pane exists (`portal-live-timeline-v0.md` M1, unbuilt as of this draft), its frame→mark adapter (§3.3) gains a mapping for `github.*` frames, with cases in the shared parity fixture (§3.1). That proposal's §3.7 calls the adapter replaceable, so the mapping lives in whatever replaces it. Both views draw these events as marks on the agent's row. A mistake renders as its path: a failing `ci_result` linked to the next passing run on the same PR, a `review_record` with its later disposition, a `claim_checked` pair with whatever closed it. Nothing is drawn in alarm colours.

## 5. What it stays out of

- **EISV and the registered read.** No `audit.outcome_events` rows and no `/v1/harness/outcome` calls in stage 1. The 12-01 read's data boundary is already fixed at 2026-10-15T13:45Z (`eisv_ablation_matrix.py`), so rows written now cannot enter it either way. The reason to stay out is what comes after: the stop rule treats labels from a new trusted verification source as a possible new label channel that needs its own registration, and outcome rows also feed calibration and the unregistered instruments. Promotion to graded outcomes is a separate operator decision after the 12-01 read reports (§8). The operator directed an opt-in stage 4 writer on 2026-11-20 (§6b); with its flag off, this paragraph still describes the observer.
- **Enforcement.** No pause, verdict, trust-tier or risk input. Events are a record for people and agents to read.
- **Wave 3 measured paths.** The observer calls no dialectic code. Option B originally assumed `broadcast_event` only emitted frames; because unmodified `broadcast_event` unconditionally schedules `_persist_event` -> `append_audit_event_async` (which would double-write `audit.events`), Stage 1 Part 2 adds a backwards-compatible `persist: bool = True` keyword parameter (all existing callers keep `persist=True` unchanged) so `POST /v1/external/events` persists atomically via `record_external_event_async` and calls `broadcast_event(..., persist=False)`.
- **Writing to GitHub.** A read-only token. The observer comments on nothing, labels nothing and merges nothing.

## 6a. Stage 1 build record

Stage 1 lands in two parts so the part that touches no reserved path can be read and run first.

- **Part 1, the reading half and the dry run (2026-11-14).** `agents/github_observer/`: `events.py` turns GitHub JSON into the `pr_*`, `ci_result` and `review_record` events of §4 with their fingerprints; `store.py` is the durable fingerprint set; `observer.py` is the read-only GitHub client, the poll and `python3 -m agents.github_observer --repo OWNER/NAME --dry-run`. The dry run prints the object a write would store and changes nothing, including the fingerprint store. Without `--dry-run` it exits 2. `tests/test_github_observer.py` runs against GitHub JSON recorded that day.
- **Part 2 (2026-11-19).** Added `POST /v1/external/events` (`src/http_routes/external_events.py`, operator-credential gated via `X-Unitares-Operator` or passkey CSRF session, strict `github.*` allow-list, §8.5 `pr_author` trust validation, 404 on unknown `agent_uuid`, 422 outside the `[now-180d, now+5m]` retention window so >180d historical PR events are rejected rather than rewritten to `now`, 409 durable fingerprint dedup via `audit.external_event_fingerprints` in migration `083`), `UnitaresEventWriter` in `agents/github_observer/observer.py`, the `external` kind in `GET /v1/timeline`, neutral `external` pane mappings in `elixir/portal`, `elixir/dialectic_live`, and `dashboard/redesign/sections/timeline.js`, plus shared parity cases in `tests/fixtures/timeline_parity/frames.json`.

Choices part 1 made inside §4, for the part 2 reviewer to confirm or change:

- **Fingerprints key on GitHub's repository id,** not the name §4's table writes as `repo`. The configured spelling (`Owner/Repo` or `owner/repo`) and a rename then leave every fingerprint where it was. The event still carries the name for reading.
- **Subject.** The last `UNITARES agent:` line a reader of the rendered body would see, in the strict 8-4-4-4-12 form: a plain-text line of a paragraph (split at line breaks) whose only enclosing elements are plain containers (`<div>`, lists), so not inside a block quote, code, a link, a table, struck-through or other formatted text, or a `<details>` or `<pre>` element. It is read from GitHub's own rendering of the body (`body_html`, requested with the `application/vnd.github.full+json` media type), not from the Markdown (#3277). GitHub has already resolved the Markdown and the HTML tree and stripped comments, so its output is balanced, and `footer.py` walks it with the standard library's HTML parser alone. Input that is not balanced, or that carries a comment, is refused rather than guessed at, and the pull request counts as a failed read. Two approaches were tried first: a hand-written Markdown line scanner, and markdown-it-py followed by an emulation of HTML's tree building. Review kept finding edge cases in both, and the second missed a validly signed pull request (#3245, whose prose holds a `<name>` placeholder). A test fixture holds GitHub's rendering of every footer test body, each with the footer read by hand. The delivery contract keeps the opening author's signature last, so a pull request with a successor is attributed to its opening author.
- **Who may sign.** Anyone can type an agent's uuid into a pull request body. A pull request is read only when GitHub's own record of its author is one the review gate would admit: an owner, member or collaborator, or the bot of a registered App. Others are counted (`prs_untrusted_author`) and skipped, and every event carries `pr_author` (association, actor id, type). This is the conservative reading; relaxing it is §8.5.
- **Which runs belong to a pull request.** A run whose head commit is one of the PR's commits or its current head, or whose `pull_requests` association names the PR by number and base repository id, which keeps the results of a head the agent amended or force-pushed away. A branch name can be reused, so it is not the key; `pull_requests` is empty on fork runs and once the PR closes, so it supplements the commit list and does not replace it.
- **Re-runs.** GitHub's run list carries one entry per run at its latest attempt. Each earlier attempt is read separately, so a failure that a re-run then passed is reported as its own fact.
- **A run waiting for approval** lists as completed with `action_required` and later finishes under the same run id and attempt. It is not reported.
- **Coverage of other check apps.** Read for the current head only, every run of each check name (`filter=all`), so an earlier failure that a re-run passed is kept. A non-Actions check on an earlier head is reported only if a poll saw it while that head was current. A check run that a workflow creates through the API under the Actions app, other than the review check, is not reported: nothing in the list distinguishes it from the workflow's own jobs.
- **The `review` check.** Left out by name, as §4 says. The workflow that posts it is still reported as a CI run; `--skip-check` adds a name to leave out.
- **State events carry `head_sha_at_observation`,** the head when the observer read the pull request. GitHub's timeline does not record the head at a close or reopen.
- **Trusted Apps.** The gate's App allow-list lives in the gate's checkout. The observer takes the same pairs (`APP_ID:BOT_ACTOR_ID`) from `--trusted-app` or `GITHUB_OBSERVER_TRUSTED_APPS` and ships none. Tests compare the admission rule with the gate's over a matrix of comment shapes, and pin the marker pattern and its tokenising to the gate's.
- **Repositories.** `--repo` is required. §8.2's default, every repository the token covers, is not ruled on.
- **Reads per poll.** Failed jobs and earlier attempts are read only for facts not yet in the fingerprint store. A list longer than ten pages of 100 fails that pull request for the poll (`prs_failed`) instead of returning a short answer. A redirect from the API is refused, so the token goes to the configured host only.
- **Exit status.** 0 for a clean poll, 1 when a repository or pull request could not be read, 2 for a usage or configuration error.

## 7. Success criteria

- Every agent-signed PR in the window has its CI conclusions and review records on the agent's timeline row within one poll interval.
- Re-polling produces no duplicates, including across an observer or server restart: durable fingerprint dedup is tested, and a CI re-run and a review disposition on the same head each appear once.
- A marker comment from an untrusted author is ignored.
- An unsigned PR, or one with a uuid unknown to UNITARES, is skipped and counted, never guessed at.
- Dry-run output matches what a write would store.
- No row lands in `audit.outcome_events`, and the registered-read manifest is untouched.
- A reader can follow one mistake from introduction to fix on the timeline without opening GitHub.

## 6b. Stage 4 writer, drafted ahead of §8.4 (2026-11-20)

**Direction.** The operator's daily grading run (a Claude Duet routine) recorded nothing for three nights: `record_result` records only for the caller's own bound agent, and that run cannot read GitHub. On 2026-11-20 the operator was shown this document's §5 and the 2026-11-14 ruling that holds graded outcomes until after the 12-01 read, and chose to build the writer now. This section records that choice; it does not rule §8.4, and the writer is off unless a deployment passes `--record-outcomes`.

**What it writes.** `agents/github_observer/outcomes.py` maps `github.pr_merged` to `task_completed`, and nothing else. CI results, closes without a merge, openings and review records stay timeline events. Each outcome posts to `POST /v1/harness/outcome` under the operator credential, with `verification_source="external_signal"`, the footer's `agent_uuid` as subject, and `detail.producer="github_observer"` plus the event's fingerprint, repository, PR, merge commit and observation time. No `confidence` is sent, so the server stamps each row `calibration_excluded`; no `prediction_id` is sent, as that route requires.

**Attribution.** The harness outcome route records `agent_uuid` as given and checks nothing about it. The event route checks the subject uuid against UNITARES and `pr_author` against the trusted list (§8.5) before its dedup, so an outcome follows only an event that route stored. Before posting a merge event the observer queues its outcome, built from the event as posted, in a `pending_outcomes` table in the fingerprint store. A 201 releases the outcome as just posted. A 409 releases it only when this store queued it on an earlier attempt whose answer was lost, and then releases that attempt's body, so a footer edited in between cannot move the outcome to another agent. A 409 for an event this store never queued (another writer, or a merge stored before the flag was turned on) records nothing. A refusal (unknown agent, untrusted author, future timestamp, 4xx) drops the queued outcome. A lost answer keeps it queued, unreleased, for the next attempt.

**Delivery.** Released outcomes are sent as each poll ends, including after a read error, and independent of whether GitHub still lists the pull request. A written outcome is recorded as `outcome:<event fingerprint>` in the fingerprint store and leaves the queue. A failed one stays queued and the poll exits 1. A 400 or 422 is the body itself being refused: it is recorded so it is not resent, counted as `outcomes_rejected`, and the poll exits 1.

**Review.** A two-family council (OpenAI and Google host adapters, council `bed54824-e383-47db-8dfd-999d84885c9b`) reviewed the first draft, which also graded CI. Its findings and what changed:

- *P1, grading CI.* A `test_failed` row for every red run on an open PR, once per workflow and re-run, contradicts the 2026-10-23 direction and biases the labels toward the agents that iterate in the open. Changed: merges only. Which CI verdict should grade, if any (for example post-merge CI on the merge commit), is left to §8.4.
- *P1, outcomes after a 409.* The first draft posted an outcome whenever the event route answered 409, which could grade an event this observer never validated, or with a footer edited since. Changed: the pending queue above.
- *P1, duplicates.* The harness route has no idempotency key. Kept as a residual: an outcome whose write committed but whose answer was lost is sent again, so a duplicate row is possible there, and a lost row is not. The fix is server-side (an idempotency key on `POST /v1/harness/outcome`, or a unique index on `detail->>'github_event_fingerprint'`), a follow-up outside this change.
- *P2, silent 400.* Changed: 400 and 422 are counted and fail the poll.
- *P2, snapshot timing.* An outcome is joined to the agent's EISV state when it is ingested, which can be up to one poll interval (and any retry delay) after the merge. Recorded here; not changed.
- *P2, producer.* The rows are told apart from other `external_signal` rows only by `detail.producer`. Recorded; a separate verification source would be a new label channel by the stop rule's definition, which this change avoids.
- *P3.* Merges stored before the flag was turned on are never graded (no backfill), and `events_known` counts are unchanged by the flag.

**What it changes, for the reviewer.**

- *Registered read.* The 12-01 read's data boundary is 2026-10-15T13:45Z, so no row this writer makes can enter it. By the stop rule's definition these rows are not a new label channel: `external_signal` is already in the anchor registry as `TRUSTED_EXTERNAL`, and `task_completed` is an outcome kind that channel scores. They are a new producer feeding that existing trusted channel, after the cutoff. Any later read, re-run or registration over a window after 2026-11-20 would include them; that is the decision §8.4 left to the operator, now taken ahead of the read.
- *Mistakes as paths (§2).* With merges only, nothing the observer writes is a bad outcome, so the 2026-10-23 direction holds. The cost is a one-sided label: only successes are graded from GitHub.
- *Calibration.* Excluded by the missing confidence; other instruments that read `audit.outcome_events` see the rows.
