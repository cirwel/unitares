# UNITARES 4.0.0 upgrade notes

This release makes inferred policy actuation an explicit deployment choice,
adds durable checkpoint acceptance and outcome-calibration delivery, and ships
the optional local operator hub. The complete change list is in the
[4.0.0 changelog](../CHANGELOG.md#400---2026-11-06).

## Before upgrading

1. Choose the policy posture. The default is now
   `UNITARES_POLICY_ACTUATION=observe`: fresh check-ins still run EISV and
   record its recommendation, but an inferred pause does not create a
   lifecycle hold. To preserve automatic actuation, set
   `UNITARES_POLICY_ACTUATION=enforce` in the server environment before
   upgrading. Existing durable pauses, authentication and authorization
   failures, archive state, and bounded loop cooldowns remain enforced.
2. Back up the database and deployment configuration, stop existing writers,
   and use the installation's documented update/migration procedure. Apply
   migration 080 (durable outcome-calibration delivery) and 081 (neutral
   checkpoints) before starting the new server. The optional hub needs manual
   migration 079 before `UNITARES_HUB_CALLBACK_URL` is enabled.
3. Check sensor settings. `UNITARES_NEUTRALIZE_SENSOR_SELF_LOOPS` and
   `UNITARES_PER_AGENT_I_CALIBRATION` now default to enabled. Set either to
   `0` to opt out of that change. The SN1 instrument era changes observed
   sensor distributions; compare readings with their instrument provenance,
   and review thresholds used by an explicitly enforcing deployment.
4. Preserve Python compatibility: the container and development defaults use
   Python 3.15; native server installations may still use Python 3.14, and
   the SDK still supports Python 3.12+. The default change does not raise
   either package's minimum interpreter version.

The server major version marks the changed actuation default. The separately
versioned negotiated interface is `2.4.1` (previously `2.3.0` in server 3.6.0).
Existing tool spellings remain available; the finding aliases now advertise
inputs their handlers already require.

## Database and rollback scope

Migration 079 creates hub sign-in code/session tables; 080 creates durable
calibration delivery/receipt tables and updates prediction-binding cleanup;
081 creates checkpoint streams, immutable checkpoint records/events, and
assessment-delivery claims. None rewrites existing lifecycle-hold rows.

A schema inspection is not a rolling-upgrade or downgrade acceptance test.
Mixed 3.6/4.0 writers and downgrade behavior have not been validated. Use a
stopped-writer migration window; retain the pre-upgrade backup and restore
code, schema and state together if rollback is required. Do not delete
checkpoint or pending delivery records to make an older process start.

## Client and service changes

- The in-tree SDK is `0.6.2`. `onboard(retry=False)` disables transport retries
  for a single mint attempt; on an ambiguous timeout the host must reconcile
  before minting again. The option is client-side and is not a new server
  parameter. Existing callers retain their default retry behavior.
- Check-in responses distinguish checkpoint acceptance, assessment execution,
  and assessment-state persistence. A receipt saying execution completed is
  not a claim that every downstream effect committed atomically.
- The optional hub uses a dashboard passkey handoff, an owner-only socket,
  digest-configured hub credentials, and a separate read-only timeline key.
  The [hub design and configuration](../proposals/active/portal-hub-v0.md)
  describe this opt-in service.
- Administrative recovery and archival mutations require operator authority.
  Per-agent REST tokens authorize only their bound agent's check-ins and do
  not grant identity recovery or fleet administration.
