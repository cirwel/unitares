# UNITARES v2.18.0 release errata

The original v2.18.0 changelog and GitHub release body omitted two merged changes and conflated several citations. This record corrects the release history without moving or replacing the public `v2.18.0` tag.

## Corrected release-note entries

### Added

- **dialectic/evaluation:** ground reviewer responses in evidence, label the frozen verdict cohort, and add recovery and reassignment coverage (#1604, #1609, #1611)
- **governance:** add measurement-only shadowing for legacy coherence dependencies and clarify cold-start actuation provenance (#1615, #1619)
- **residents/local models:** extract the reusable local-model member lifecycle and add the triage-scribe resident as a second live-verified consumer (#1621)
- **SDK/docs:** publish the SDK README as package metadata and document the operational federation path (#1613, #1616)

### Changed

- **public surface:** add dedicated knowledge write aliases, correct advertised dialectic actions, and make inference-host reachability explicit (#1610)
- **release/operations:** professionalize the public release surface, tighten evaluator claims, and bound persisted risk history (#1603, #1612, #1617)
- **security/release:** redact caller-controlled identity/session material from logs, pin external actions, and tighten workflow permissions (#1620)
- **dependencies:** refresh Python, cryptography, and dashboard development dependencies (#1556, #1557, #1558)

### Fixed

- **governance/eisv:** separate legacy control feedback from coherence and preserve causal provenance without changing the advisory policy posture (#1614)
- **dialectic:** harden evidence handling and reviewer recovery so standing rejections and synthetic reviews cannot be cleared or misrepresented (#1604, #1611)
- **telemetry:** state explicitly which tool-usage fields the public read surface can support (#1618)
- **operations/deploy:** compare deployed build SHAs, count post-restart merge changes correctly, and surface checkout-behind drift for LIVE/HOT-RELOAD/STALE services (#1622)

### Documentation

- **project framing:** consolidate public entry points, publish evaluator-facing limitations, and document federation as a research direction rather than a deployed guarantee (#1603, #1612, #1616)

## Compatibility correction

The v2.18.0 release-time compatibility table described `unitares-governance` plugin `v0.4.13` as aligned with server `v2.18.0`. That wording was too strong: `v0.4.13` is the package-alignment release from 2026-08-11 and predates the coherence-semantics skill synchronization merged in plugin PR #116. The compatibility table now distinguishes package compatibility from semantic-skill alignment. A later tagged plugin release should carry the synchronized skill bundle.

**Closed 2026-08-21.** Plugin `v0.4.14` carries it. Its `skills/` bundle is a byte-identical mirror of this repository's `skills/` at the `v2.19.0` release, verified file-by-file and against the published `SKILLS_MANIFEST.sha256`, and includes both plugin PR #116 and the v2.19.0 margin-semantics correction. The compatibility table's plugin row now reads "aligned with server `v2.19.0`", and `version_manager.py` tracks the stronger wording so a future weakening fails the check.

## Docker quickstart validation gap

The v2.18.0 release PR reported the Docker quickstart as delegated to required CI because the local Docker daemon was unavailable. The required CI run did not contain the documented Docker quickstart. Because #1556 changed the pinned Python container input, the release-process requirement applied. Therefore Docker quickstart validation for the immutable v2.18.0 tag remains **unverified until an actual Docker-capable run is recorded**; a green Python/package CI run must not be treated as equivalent evidence.

**Validation recorded 2026-08-21.** The documented quickstart was run against the immutable `v2.18.0` tag on a Docker-capable host (Docker Engine 29.1.3, macOS): fresh `git clone --branch v2.18.0 --depth 1`, `docker compose up -d --wait` with all services healthy, then `make demo`, which onboarded an agent and completed all six check-ins against the containerized server. Host-side ports were remapped through the compose file's own `.env` overrides (`POSTGRES_HOST_PORT=15432`, `REDIS_HOST_PORT=16379`, `GOVERNANCE_HOST_PORT=18767`, with `UNITARES_DEMO_PORT=18767` for the demo) to coexist with a live deployment on the default ports; container-side behavior is unmodified. This closes the validation gap above.
