# UNITARES v2.19.0 release errata

The v2.19.0 changelog entry and GitHub release body omitted thirteen merged pull
requests. This record corrects the release history without moving or replacing
the public `v2.19.0` tag.

## What was omitted

Thirteen pull requests, #1625 through #1637, landed in the `v2.18.0..v2.19.0`
range as **merge commits** rather than squashes. None of their numbers appear in
the published entry.

Corrected coverage for v2.19.0 is **133 of 147** merged pull requests, not the
132 of 133 claimed while the release was being prepared. The two remaining
uncited numbers are #1788 and #1789, this release's own version-bump and
changelog pull requests, which cannot appear in the entry they create.

Six of the thirteen are **absent from the entry entirely**:

### Added

- **eisv/inference:** re-land the call-gate disclosure on the inference-host discovery reads that #1610 dropped (#1627)

### Changed

- **governance:** retire legacy coherence as a governance authority (#1626)
- **ci/scope:** auto-remove the harness attribution footer instead of failing the check on it, and correct a false-dead registry row (#1637)

### Fixed

- **triage-scribe:** read the fields `observe` actually returns (#1628)
- **watcher:** let a finding outlive the file it was found in (#1631)

### Documentation

- **dev:** generate the tool edge index from the live registries (#1634)

Seven are **described in the entry but carry no pull-request number**, so a
reader cannot trace the claim back to the change: #1625 (CI database and test
schema drift), #1629 (the dialectic sweeper's failure reason), #1630 (reporting
a pinned deploy that falls behind a version), #1632 (clamping lifecycle
`agent_id` to a joinable key or NULL), #1633 (repairing partially applied
migration 034 and adding the `constraint_drift` doctor check), #1635 (anchoring
the schema registry to file content), and #1636 (the general solution of the
reduced three-state EISV core).

## Why the coverage check did not catch it

`scripts/ci/changelog_coverage.py` shipped in this release specifically to
prevent an incomplete entry. It did not, and it reported the incomplete entry as
complete: `covers 131/131`, exit 0.

Its denominator came from `git log --no-merges`, taking each commit subject's
trailing `(#N)`. This repository allows squash, merge, and rebase merges, and
does not require linear history, so a pull request merged as a merge commit has
no such subject and was never counted. The check was measuring the pull requests
it could see, and reporting that number as if it were the total.

A denominator that a merge-method choice can silently shrink is not a
denominator. The fix is tracked separately; it must derive the merged set from
an authoritative source rather than from commit-subject archaeology, and must
fail as indeterminate rather than pass when the baseline cannot be established.

## Corrections applied

`docs/CHANGELOG.md` now carries all thirteen. The changelog is a living file and
is corrected in place; the `v2.19.0` tag is immutable and is unchanged. The
GitHub release body carries this errata as an appended section, with the
original text preserved above it.
