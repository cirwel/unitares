## Publication checklist

1. Review the diff against v2.22.0, the upgrade instructions and version choice.
2. Require all candidate CI, including the actual Docker MCP checks, to pass.
3. Merge only into `release/2.22`, then tag that exact merge commit as v2.22.1.
4. Publish the release and verify both container architectures, digest, SBOM
   and build provenance. Publication leaves `latest` unchanged; only after
   verification promote the inspected index digest using RELEASE_PROCESS.
   Leave v2.22.0's tag unchanged.
5. Append the v2.22.0 errata to its existing release body.
6. Integrate the tagged maintenance history and verified public install pin
   through a reviewed master PR, preserving newer mainline code. The next
   mainline release must include this tag in its ancestry; assess its version
   separately from this maintenance artifact.

Tagging, publication and the master forward-merge are complete.
`PUBLISHED_VERSION` still reads 2.21.0, so public installation examples stay
pinned to v2.21.0 until the step 4 verification is recorded and the pin is
advanced through a reviewed master PR. Source preparation, merge, tagging,
