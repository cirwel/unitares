# AX dogfood read: task state without UNITARES internals (2026-10-16)

**Status:** exploratory. One agent ran three tasks once against one deployment,
and the same agent applied the labels. This is not a usability result, not a
comparison against another tool, and not evidence about other harnesses or
models.
**Tracker:** cirwel/unitares#2342 step 6.
**Builds on:** the agent-experience (AX) notes in the knowledge graph:
`2026-09-20T21:21:29.873568+00:00` (AX as a quality dimension),
`2026-09-21T07:01:03.014933+00:00` (Antigravity: tool count, ~6.4 KB check-in),
`2026-09-22T17:48:57.864458+00:00` (MiMo research trace: the north star,
the 2–3 call target, and this labelling scheme), and
`2026-10-03T06:08:53.317893+00:00` (Claude chat client: jargon, payload size,
`store_finding` not advertised). Those notes are qualitative. This read adds a
per-call record: bytes, latency, the fields each task needed, and the
UNITARES-internal concepts the agent had to understand to use them.

## Question

Can an agent get the task state it needs from UNITARES without first learning
UNITARES internals? The AX north star in `2026-09-22T17:48:57` is to make
epistemic distinctions visible while hiding transport and bookkeeping. The
target is about 2–3 UNITARES calls for a common search → act → record
workflow, with lean responses.

## Protocol (fixed before the run)

**Client.** A raw MCP streamable-HTTP client (`initialize`, `tools/list`,
`tools/call`) against the live governance server on `localhost:8767/mcp/`,
using the operator's bearer token. Using a raw client, rather than this
harness's own MCP connection, means the run holds its own identity and does not
inherit the harness's binding, hooks or prompt context. Each task starts from
the advertised `tools/list`, with no prior knowledge of hidden tools assumed.
One identity is used for the whole run: `start_session(force_new=true)` once,
no name, with `client_session_id` passed on later calls. `identity()` is never
called without arguments.

**Tasks.**

1. **Prior-work check.** "Before starting work on *a skill-freshness CI
   failure after editing a document that a skill cites*, find out whether
   prior work exists." Task fields needed: for each relevant entry, its id,
   summary and status, and enough to decide yes or no. No identity is needed
   for this read.
2. **Where do I stand.** "Report my current state, whether I am paused, and
   whether my writes will be held." Task fields needed: the policy action
   (proceed, guide or pause), whether writes are held, and the reason in one
   line.
3. **Record and confirm.** "Record a status pointer on an existing finding,
   then confirm that a later search surfaces it." The pointer is real: the
   MiMo-V2.6 shadow-evaluation protocol note (`2026-09-22T17:27:21.756262+00:00`)
   was never filed and is now linked in the canonical contract as a proposed,
   not-started path (#2845). Task fields needed: the new entry's id, that it is
   linked to the protocol note, and that a search returns it.

**Measures per call.** Tool; purpose; request and response bytes (the
JSON-RPC body); wall-clock latency; the fields the task actually used; the
UNITARES-specific concepts the agent had to understand to use the response
or to make the next call (for example session plumbing, aliases, response
modes, epistemic labels, routing between overlapping tools); and whether the
call was a plumbing step (identity, session or discovery) rather than task
work.

**Per task.** Calls, total and median response bytes, plumbing steps,
whether the task was completed, and a stated judgement of whether the task
information gained exceeded the UNITARES-specific information the agent had
to learn.

**Labels.** Each call gets one label:

- `burden_reduced`: the call gave task information the agent would
  otherwise have had to obtain more expensively (prior work, current state, a
  durable record).
- `burden_justified`: the call cost something, but that cost buys a
  distinction the task needs (identity binding for an attributed write;
  provenance that changes what the agent may conclude).
- `burden_accidental`: the cost was not needed by the task. Examples are
  discovery calls just to reach a tool, required interpretation of internal
  vocabulary, or payload the task did not use.

Within a call, payload the task did not need is reported separately as
"unused bytes" rather than relabelling the call. A single rater labels the
calls, and that rater also ran the tasks.

**Not measured.** Token counts (bytes are reported instead), model quality,
any EISV value, and anything about other clients.

**Did task information exceed what the agent had to learn?**

- **T1: yes.** The answer needed only the summaries and the low-confidence
  flag.
- **T2: yes, narrowly.** The answer came in a 1.2 KB response. To get there,
  the agent had to learn that `check_working_state` does not initialize state,
  and that `proceed` implies writes are not held.
- **T3: depends on the variant.** A plain record needs one call. A linked
  record needed a 7 KB schema read, the router vocabulary and a guessed enum
  value. That is more UNITARES-specific information than the one link it bought.

## Findings

Each task met the 2–3 call target. The three tasks together took 9 calls, so
a full search → act → record session that also needs identity and a link
costs more than the target.

**Compared with the earlier notes** (all version-dependent; this is server
3.3.0):

- `store_finding` is now advertised (2026-10-03 item 4 is resolved).
- A routine `sync_state` returned 1.2 KB. The 2026-09-21 note reported about
  6.4 KB in compact mode.
- `check_working_state` returned 1.5 KB by default. The 2026-10-03 note
  reported 4.6 KB at `verbosity=standard`.
- `start_session` returned 1.1 KB, without the resident-roster jargon that the
  2026-10-03 note flagged.

**Epistemic distinctions were visible where they mattered:** the
low-confidence search flag, the provisional verdict with its caveat, and the
typed response link. That is the north star's first half. The second half,
hiding bookkeeping, holds less well: about 74% of returned bytes were not
used by these tasks.

## Accidental-burden items (candidates, not decisions)

New tools, aliases, actions or parameters are operator-reserved (`docs/integration/INTENT_MAP.md`); each item below is a candidate for that review, not a change made here.

1. **The search digest shows 3 of N with nothing about the rest.** Here that
   was 3 of 20, which forced call 3. A one-line id and summary for the
   remainder would settle "is there more?" without a 32 KB full read. An
   earlier bound-identity lean search on the same day did list
   `more_results`; this unbound one did not. The cause was not established.
2. **Two relevance scales appear in one result list** (`lexical_rank_only`
   around 0.016, semantic around 0.5), with nothing saying they are not
   comparable.
3. **Search hints name a tool that is not advertised.** They point to
   `knowledge(action='details')`, which a client sees only through
   `use_tool(tool_name='knowledge', …)`. The hint could name the reachable form.
4. **No explicit hold status on a fresh identity.** `check_working_state`
   answers `uninitialized` and does not say whether the agent is paused or its
   writes are held. An explicit hold field in `action_summary` would answer T2
   in the read-only call.
5. **`store_finding` cannot record a link.** Linking needs `describe_tool` plus
   `use_tool(knowledge, store)` (7.2 KB plus 3.4 KB). A `response_to` on
   `store_finding` would make a linked record one call. That is a new
   parameter, so it is for operator review.
6. **The valid `response_type` values are not listed in the schema.** Its
   description gives only the shape.
7. **The store response repeats identity and attaches an EISV snapshot.** The
   identity block appears twice, and the snapshot sits under `provenance`.
   The task used about 5% of that response.
8. **The weak assurance at mint is unexplained.** `start_session` reports
   `tier: weak`, `caller_proven: false` at mint for a bearer `/mcp/` client.
   The explanation (it describes the minting call, so confirm on the next
   call) is in the repo contract, not in the response. The next write
   reported `tier: strong`. *Correction, 2026-10-17:* this item first said
   the client sent an `Mcp-Session-Id`. It did not. `/mcp/` is served
   stateless (`build_streamable_session_manager(stateless=True)`), so the
   server issues no session id, and the client sends one only after
   receiving one; its saved state held none. The mint therefore carried no
   session signal, which is the case the contract describes, not a defect.
   The `start_session` response now carries the explanation in
   `next_action`.
9. **Router vocabulary in the `store_finding` schema.** Its field descriptions
   carry phrases such as "for action=store or promote", "action=search" and
   "S22 H5 provenance". This is the same class as the `search_shared_memory`
   issue fixed in #2627.
10. **Mixed signals on routine check-ins.** `sync_state` says `status: healthy`
    next to the caveat that this is "not a validated all-clear", and it
    surfaces a coherence value labelled "not health-rated". The caveat is the
    accurate part; the word "healthy" works against it.

## Limits

- One agent ran three tasks once, and the same agent applied the labels.
- The tasks were chosen by the rater.
- The client was a raw MCP client, not a model harness. It therefore measured
  payloads and call sequences, not how a model reads them.
- "Used" bytes are a judgement.
- No other harness, model or server version was tested.
