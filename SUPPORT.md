# Support

UNITARES is an independent, solo-maintained research implementation. Support is
best-effort; there is no response-time or uptime SLA.

| Need | Use |
|---|---|
| Reproducible defect in a supported release | [Bug report](https://github.com/cirwel/unitares/issues/new?template=bug_report.yml) |
| Feature or integration proposal | [Feature request](https://github.com/cirwel/unitares/issues/new?template=feature_request.yml) |
| Usage, setup, or design question | [GitHub Discussions](https://github.com/cirwel/unitares/discussions) |
| Security vulnerability | [Private vulnerability reporting](https://github.com/cirwel/unitares/security/advisories/new) |
| Conduct concern | Follow the private-contact procedure in [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) |

Only the current `master` branch and latest tagged server release receive fixes.
The exact security-support boundary is in [SECURITY.md](SECURITY.md); component
and client versions are mapped in [COMPATIBILITY.md](COMPATIBILITY.md).

## What best-effort means

Reports are prioritized by reproducibility, user impact, and security risk. The
maintainer may ask for a smaller reproduction or close reports that cannot be
reproduced. Feature proposals can remain open without a delivery commitment.
Security acknowledgements follow the separate timeline in `SECURITY.md`.

Before filing a public report, remove access tokens, private telemetry, database
contents, and agent identifiers you do not want disclosed. A useful report
includes the UNITARES version, environment, smallest reproduction, expected
behavior, actual behavior, and sanitized evidence.
