# Pip constraints applied to CI installs and the Docker image so the tested
# and shipped dependency resolution matches what production actually runs.
#
# Why this file exists: the ranges in requirements-*.txt float, so "what CI
# tests" silently changes whenever a new release appears on PyPI. That is how
# mcp 2.0.0 became CI's de-facto tested version in August 2026 with no commit
# and no decision, while production stayed on 1.x — and 2.0.0 carries client
# breaks the mocked test suite cannot see (see tests/test_mcp_dependency_canary.py).
#
# Policy: pin here only dependencies where CI/production drift has actually
# bitten. Bump a pin deliberately, in the same PR that prepares the production
# move (and deploy the interpreter bump with it). The `mcp-newest` advisory CI
# job tests the newest in-range resolution WITHOUT these constraints, so
# coverage of upcoming versions is a deliberate lane, not an accident.
#
# How to apply this file, and the one way it silently does not work:
#
#   pip install -r requirements-full.txt -c constraints.txt
#
# A constraint binds only when pip decides to install a package. It does NOT
# downgrade something already present that satisfies the requirement range. So
# on an environment that already resolved a newer version — a long-lived venv,
# or one seeded by `pip install -e .`, whose ranges float — the command above
# leaves that newer version in place and reports success. CI never hits this
# because every run starts from a clean image; a developer's venv does.
#
# The failure is not subtle once it happens (an env carrying mcp 2.x fails to
# COLLECT most of the suite, not merely to pass it), but the install that
# caused it looked clean. On an existing environment, pin explicitly:
#
#   pip install "mcp==1.29.0" -r requirements-full.txt -c constraints.txt
#
# or rebuild the venv. `pip check` will not catch it: the newer version
# satisfies every declared range, which is exactly why this file exists.
#
# mcp 2.x gate. The transport is written against httpx2 while our client-side
# call sites injected httpx 0.x, which killed the server-push GET stream
# SILENTLY. Moving this pin to 2.x needs ALL of:
#
#   [done] the httpx2 injection port — call sites now build their injected
#          client from `mcp_httpx()` (src/mcp_compat.py, and the SDK's own
#          copy in unitares_sdk/_mcp_httpx.py), which reads the library off
#          the installed transport instead of hardcoding one.
#   [done] a widened `mcp` pin in agents/sdk/pyproject.toml (otherwise the
#          constrained sdk-package install hard-errors on the conflict).
#   [done] a green mcp-newest lane — the advisory job resolves mcp 2.x and
#          tests/test_mcp_dependency_canary.py passes against it.
#   [    ] the production interpreter bump, deployed alongside the flip.
#
# The pin stays at 1.29.0 until that last item is an operator decision made
# with a deploy, not a merge: bumping it here changes what production installs.
mcp==1.29.0
